\section{Interacciones síncronas: sockets y RPC}
\label{sec:sincronas}

En OndaPlay, algunas operaciones deben esperar la respuesta de otro servicio antes de continuar. Es el caso del inicio de sesión, la consulta del catálogo, la autorización de una reproducción y la entrega de segmentos de video. Aunque la comunicación sea síncrona, el reproductor puede seguir mostrando el contenido que ya tiene en su búfer mientras espera un nuevo segmento.

Se identificaron cinco interacciones. S1 utiliza sockets TCP para solicitar segmentos de video; S2, S3, S4 y S5 emplean gRPC sobre HTTP/2 para las llamadas entre servicios. Cada elección se relaciona con las necesidades de OndaPlay y con los requisitos del escenario.

\subsection{S1: Solicitud de segmento de video (sockets TCP)}
\label{sub:s1}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Reproductor (CLI) $\rightarrow$ Nodo de borde (VID). La petición llega al nodo encargado de entregar el video, sin pasar por el API Gateway.

    \item \textbf{Mensaje:}
    El reproductor envía una solicitud JSON con el identificador del contenido, el número de segmento, la calidad y el token de licencia. VID verifica el token y, si la petición es válida, devuelve la longitud del segmento seguida de sus datos binarios. Esta delimitación permite saber cuántos bytes debe recibir el cliente.

    \item \textbf{Tipo:} Sockets TCP.

    \item \textbf{Por qué es síncrona:}
    Para procesar el segmento solicitado, el reproductor debe esperar a que VID lo entregue. Esa espera no impide mostrar los segmentos que ya estén almacenados en el búfer.

    \item \textbf{Protocolo:} TCP.

    \item \textbf{Middleware:}
    No se requiere middleware de mensajería. Se plantea una conexión directa mediante sockets TCP, con un formato definido para distinguir las solicitudes y los segmentos recibidos.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Latencia:}
        R2 establece que la reproducción debe comenzar en menos de 2 segundos. Enviar la solicitud directamente a VID evita una llamada adicional al Gateway durante la entrega del segmento. Sin embargo, el cumplimiento de R2 también depende del tiempo de autorización, la red y la disponibilidad del primer segmento.

        \item \textit{Volumen:}
        R1 contempla hasta 50\,000 espectadores simultáneos. Por eso, la entrega debe repartirse entre varios nodos de borde; un solo nodo no sería una base adecuada para atender toda esa carga.

        \item \textit{Respuesta inmediata:}
        Se requiere una respuesta dentro del tiempo disponible antes de que se vacíe el búfer. Si el segmento tarda demasiado, el video puede detenerse.

        \item \textit{Si no responde:}
        Si un nodo falla (F3), el reproductor espera hasta el tiempo límite configurado e intenta solicitar el segmento a otro nodo disponible. Si tampoco lo obtiene, puede producirse una interrupción.

        \item \textit{Consistencia:}
        El contenido, número y versión identifican cada segmento. En una transmisión en vivo, los nodos pueden recibirlo en momentos distintos; por eso, el reproductor debe recibir la versión correspondiente a la secuencia que está reproduciendo.
    \end{itemize}

    \item \textbf{Alternativa descartada:}
    HLS sobre HTTP con una CDN es una alternativa habitual para distribuir video. Aquí se proponen sockets TCP para representar de forma explícita el intercambio directo entre CLI y VID; a cambio, es necesario definir el formato de los mensajes y gestionar las conexiones y los errores.

\end{itemize}

\subsection{S2: Verificación de licencia (gRPC)}
\label{sub:s2}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Reproductor (CLI) $\rightarrow$ API Gateway (GW) $\rightarrow$ Servicio de autenticación y licencias (AUT). La llamada gRPC corresponde al tramo GW--AUT.

    \item \textbf{Mensaje:}
    GW consulta si un usuario puede reproducir un contenido determinado. AUT responde \emph{permitido} o \emph{denegado} y, si autoriza la solicitud, emite un token de licencia firmado con una duración de 3 minutos.

    \item \textbf{Tipo:} RPC.

    \item \textbf{Por qué es síncrona:}
    La autorización se necesita antes de pedir el primer segmento. Por tanto, S2 debe completarse antes de iniciar S1.

    \item \textbf{Protocolo:} HTTP/2.

    \item \textbf{Middleware:} gRPC con Protocol Buffers.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Latencia:}
        La verificación forma parte del tiempo de inicio exigido por R2. Se utiliza gRPC porque facilita las llamadas directas entre servicios, emplea mensajes binarios y puede reutilizar conexiones HTTP/2. Esto reduce trabajo de comunicación, aunque no asegura por sí solo el límite de 2 segundos.

        \item \textit{Volumen:}
        Antes de un evento en vivo pueden llegar muchas solicitudes al mismo tiempo. Se prevén varias instancias de AUT para repartir la carga asociada a R1.

        \item \textit{Respuesta inmediata:}
        Sí. Sin una autorización válida no se inicia una reproducción nueva.

        \item \textit{Si no responde:}
        Para contribuir al objetivo de disponibilidad del 99,9\,\% (R6), GW podrá recurrir a otras instancias de AUT y realizar reintentos limitados. Estas medidas aumentan la tolerancia a fallos, pero no garantizan por sí solas ese porcentaje.

        Si todas las instancias quedan fuera de servicio (F1), no se emitirán licencias nuevas. Un reproductor con token vigente podrá solicitar segmentos mientras VID siga aceptándolo. Cuando el token venza, la reproducción necesitará una nueva autorización; si AUT continúa caído, no podrá obtenerla.

        \item \textit{Consistencia:}
        AUT consulta el estado de suscripción mediante S3. Si ese estado se conserva hasta 60 segundos y el token dura 3 minutos, una licencia emitida justo antes de que caduque la información almacenada podría seguir siendo válida hasta unos 4 minutos después de una cancelación.

        Bajo esas condiciones, el diseño se mantiene dentro de los 5 minutos de R4. Para sostener ese límite, AUT no debe reutilizar datos de caché vencidos y VID debe verificar la expiración del token. El plazo describe el uso de una autorización existente; no implica que una reproducción en curso se detenga inmediatamente cuando se cancela la suscripción.
    \end{itemize}
\end{itemize}

\subsection{S3: Consulta de suscripción (gRPC)}
\label{sub:s3}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Servicio de autenticación y licencias (AUT) $\rightarrow$ Servicio de suscripciones y pagos (PAG).

    \item \textbf{Mensaje:}
    AUT envía el identificador del usuario. PAG informa si su suscripción está \emph{activa}, \emph{vencida} o \emph{cancelada}.

    \item \textbf{Tipo:} RPC.

    \item \textbf{Por qué es síncrona:}
    Si AUT no tiene un estado vigente en caché, necesita la respuesta de PAG para decidir si concede la licencia.

    \item \textbf{Protocolo:} HTTP/2.

    \item \textbf{Middleware:} gRPC con Protocol Buffers.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Latencia:}
        AUT mantiene el estado de la suscripción en caché durante un máximo de 60 segundos. Así evita consultar PAG en cada autorización y reduce una parte de la espera asociada a R2.

        \item \textit{Volumen:}
        Las solicitudes repetidas dentro de ese intervalo se atienden con el dato almacenado, lo que disminuye las llamadas a PAG cuando muchos usuarios intentan reproducir contenido.

        \item \textit{Respuesta inmediata:}
        La respuesta de PAG se necesita antes de emitir la licencia únicamente si no existe un dato de caché vigente.

        \item \textit{Si no responde:}
        AUT usa el último estado guardado solo mientras siga vigente. Si no dispone de una respuesta válida, rechaza la emisión de una licencia nueva en lugar de asumir que la suscripción continúa activa.

        \item \textit{Consistencia:}
        Se acepta consistencia eventual, con un retraso de caché de hasta 60 segundos. Además, cuando PAG registra una cancelación, envía un aviso asíncrono para que AUT invalide el dato guardado. Ese mecanismo se explica en la sección de interacciones asíncronas.

        El aviso ayuda a actualizar antes el estado, pero no revoca automáticamente los tokens emitidos. Por eso, el límite previsto en R4 depende tanto de la duración de la caché como de la vigencia del token, según lo explicado en S2.
    \end{itemize}
\end{itemize}

\subsection{S4: Exploración del catálogo (gRPC)}
\label{sub:s4}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Reproductor (CLI) $\rightarrow$ API Gateway (GW) $\rightarrow$ Servicio de catálogo (CAT). GW consulta a CAT mediante gRPC.

    \item \textbf{Mensaje:}
    El reproductor envía una búsqueda o solicita los datos de un título. CAT devuelve los resultados y, cuando corresponda, temporadas y otros metadatos.

    \item \textbf{Tipo:} RPC.

    \item \textbf{Por qué es síncrona:}
    GW necesita los resultados de CAT para responder a la consulta que acaba de realizar el usuario.

    \item \textbf{Protocolo:} HTTP/2.

    \item \textbf{Middleware:} gRPC con Protocol Buffers.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Latencia y volumen:}
        GW puede guardar durante 10 minutos los resultados de consultas frecuentes, por ejemplo, los títulos destacados durante un evento. Esto evita repetir llamadas a CAT y agiliza las búsquedas más habituales.

        \item \textit{Respuesta inmediata:}
        La consulta debe resolverse en un tiempo razonable para que el usuario pueda elegir qué ver; no requiere la misma exigencia temporal que la entrega de un segmento de video.

        \item \textit{Si no responde:}
        GW podrá mostrar una respuesta guardada si existe una versión utilizable. De lo contrario, informará que la búsqueda no está disponible. Mostrar datos anteriores evita dejar la pantalla vacía, aunque algunos detalles podrían estar desactualizados.

        \item \textit{Consistencia:}
        Se tolera un retraso en la actualización de metadatos del catálogo. Los permisos de reproducción no se deciden con esta caché, sino mediante S2 y S3.
    \end{itemize}

\end{itemize}

\subsection{S5: Inicio de sesión (gRPC)}
\label{sub:s5}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Reproductor (CLI) $\rightarrow$ API Gateway (GW) $\rightarrow$ Servicio de autenticación y licencias (AUT). Al igual que en S2, el tramo entre GW y AUT utiliza gRPC.

    \item \textbf{Mensaje:}
    El reproductor envía las credenciales de acceso a través de GW. AUT comprueba la identidad del usuario y devuelve un token de sesión si la validación es correcta; en caso contrario, rechaza el acceso. Este token no es el mismo que autoriza la reproducción en S2.

    \item \textbf{Tipo:} RPC.

    \item \textbf{Por qué es síncrona:}
    El cliente espera el resultado del inicio de sesión antes de permitir el acceso a las funciones que requieren autenticación.

    \item \textbf{Protocolo:} HTTP/2.

    \item \textbf{Middleware:} gRPC con Protocol Buffers.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Latencia:}
        El inicio de sesión ocurre antes de que el usuario pulse \emph{reproducir}; por tanto, no se incluye en los 2 segundos definidos por R2 para iniciar el video.

        \item \textit{Volumen:}
        Muchos espectadores pueden iniciar sesión poco antes de una transmisión de R1. AUT debe poder atender ese aumento de solicitudes sin afectar las verificaciones de licencia de S2.

        \item \textit{Respuesta inmediata:}
        Se necesita una confirmación para habilitar el acceso, pero no hay motivo para repetir la solicitud mientras AUT siga procesándola.

        \item \textit{Si no responde:}
        Si AUT queda fuera de servicio (F1), no se podrán iniciar sesiones nuevas. Las sesiones que ya sean válidas podrán seguir utilizándose mientras las funciones consultadas estén disponibles. Sin embargo, al vencer una licencia de S2, su renovación también dependerá de que AUT vuelva a responder.

        \item \textit{Consistencia:}
        Para evitar aceptar contraseñas anteriores o cuentas bloqueadas, la validación debe consultar información de autenticación actualizada. No basta con llamar a esta operación \emph{consistencia fuerte}: el resultado dependerá de cómo se almacenen y actualicen las credenciales y los bloqueos. S5 valida la identidad; S2 y S3 comprueban el derecho a reproducir contenido.
    \end{itemize}

\end{itemize}
