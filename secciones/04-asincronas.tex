\section{Interacciones asíncronas y tolerancia a fallos}
\label{sec:asincronas}

En la plataforma de OndaPlay empleamos comunicación asíncrona para aquellos flujos donde el emisor no requiere una respuesta rápida para continuar con su flujo de 
trabajo, priorizando la disponibilidad y la baja latencia al usuario final. Para la gestión de mensajes utilizamos dos middlewares especializados: Apache Kafka (\texttt{KFK}) para la ingesta masiva de eventos de telemetría y recomendaciones
 en tiempo real debido a su arquitectura de registro distribuido en disco, y RabbitMQ (\texttt{RMQ}) como bróker de mensajería empresarial para la transmisión
 fiable y orientada a eventos de dominio entre los servicios de facturación y licencias.

\subsection{A1: Envío de telemetría (Reproductor $\rightarrow$ Telemetría)}
\label{sub:a1}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:} 
    CLI (Reproductor en app/web/TV) $\rightarrow$ TEL (Servicio de Telemetría).

    \item \textbf{Mensaje:}
    Evento en JSON con los campos:
    \begin{itemize}
        \item \texttt{user\_id}, \texttt{session\_id}, \texttt{content\_id}
        \item \texttt{event\_type},(play, pause, buffer\_empty, quality\_change)
        \item \texttt{timestamp}, \texttt{metrics} (bitrate actual, fotogramas perdidos)

    \end{itemize}

    \item \textbf{Tipo:}
    Cliente-Servidor (Petición/Respuesta no bloqueante).

    \item \textbf{Por qué es asíncrona:}
    La petición HTTP se dispara desde un hilo secundario en el reproductor mediante una estrategia de disparo y olvido (\textit{fire-and-forget}). El cliente no bloquea la interfaz de usuario
    ni congela el buffer de video en espera de una respuesta en el servidor.

    \item \textbf{Protocolo:}
    HTTP/2 mediante peticiones REST/JSON sobre HTTPS.

    \item \textbf{Middleware:}
    No aplica a la recepción inicial; el servicio TEL recibe la petición HTTP directamente y deposita el evento en Apache Kafka (\texttt{KFK}).

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Volumen:}
        Cumple con el requisito R3 al soportar 5\,000 eventos/s generados durante transmisiones en vivo con 50\,000 espectadores emitiendo un reporte cada 10 segundos.

        \item \textit{Pérdida tolerada:}
        Según R3, se acepta perder hasta un 1\,\% de los mensajes de telemetría sin que afecte a la métrica global ni interrumpa el servicio al usuario.

        \item \textit{Alternativa descartada:}
        Se descarto gRPC sincrono porque acoplaría el hilo principal del reproductor a la latencia de red. Y asi mismo, se descarto RabbitMQ para apache Kafka debido a que RabbitMQ
        sufriría mayor degradación ante ráfagas masivas en 5\,000 eventos/s, mientras Kafka escribe en disco secuencialmente mediante logs distribuidos con mejor rendimiento.

        \item \textit{Si el receptor no responde:}
        El cliente guarda un buffer circular en memoria local de los últimos 3 a 5 eventos. Si TEL pasa más de 50 segundos caído, el reproductor empieza a descartar los paquetes mas antiguos para no saturar la RAM del dispositivo
        asumiendo que se superara el 1\,\% de pérdida pero tolerando que el video no se detenga.
         
    \end{itemize}
\end{itemize}

\subsection{A2: Eventos de visualización (Telemetría $\rightarrow$ Recomendaciones)}
\label{sub:a2}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    TEL (Servicio de Telemetría) $\rightarrow$ (\texttt{KFK}) (Apache Kafka) $\rightarrow$ REC (servicio de Recomendaciones).

    \item \textbf{Mensaje:}
    Objeto consolidado del evento visto 
    \begin{itemize}
        \item \texttt{user\_id}, \texttt{content\_id}
        \item \texttt{watch\_duration\_seconds}
        \item \texttt{completion\_percentage}, \texttt{timestamp}
    \end{itemize}
    
    \item \textbf{Tipo:}
    Publicación / Suscripción (Pub/Sub).

    \item \textbf{Por qué es asíncrona:}
    El procesamiento de algoritmos de recomendación consume bastantes recursos y no es necesario actualizar el perfil del usuario en tiempo real instante a instante.

    \item \textbf{Protocolo:}
    Protocolo binario de Kafka sobre TCP.

    \item \textbf{Middleware:}
    Apache Kafka (\texttt{KFK}) (Topic de telemetría procesada).

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Retraso aceptable:}
        Se ajusta al requisito R5, el cual permite hasta 15 minutos de retraso en la actualización del catálogo de recomendaciones (consistencia eventual).

        \item \textit{Alternativa descartada:}
        Se descartó RabbitMQ para este flujo debido a que Kafka administra la retención de datos en disco mediante particiones y archivos de registro (\textit{commit logs}) configurados con un tiempo de retención de 7 días.
        Esto permite almacenar de forma segura las 2 horas de eventos acumulados durante la caída del servicio REC (F2) sin saturar la memoria RAM del servidor ni perder el orden de los mensajes.


        \item \textit{Si el receptor no responde:}
        Frente al escenario F2 (Recomendaciones caído por 2 horas), los mensajes se quedan retenidos de forma segura en las particiones del Topic de Kafka. Al volver
         a estar en línea, el servicio REC lee desde el último \textit{offset} guardado y procesa el atraso sin perder ningún evento de visualización.
    \end{itemize}
\end{itemize}

\subsection{A3: Cambio de suscripción (Facturación $\rightarrow$ Licencias)}
\label{sub:a3}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    PAG (Servicio de Facturación) $\rightarrow$ \texttt{RMQ} (RabbitMQ) $\rightarrow$ AUT (Servicio de Licencias).

    \item \textbf{Mensaje:}
    Evento de dominio en JSON: 
    \begin{itemize}
       \item \texttt{event\_id}, \texttt{user\_id}
       \item \texttt{event\_type},(SUBSCRIPTION\_CANCELLED, RENEWED, PAYMENT\_FAILED)
       \item \texttt{expiration\_timestamp}.
    \end{itemize}
    
    
    \item \textbf{Tipo:}
    Publicación / Suscripción (Pub/Sub).

    \item \textbf{Por qué es asíncrona:}
    Evita que la pasarela de pagos o el proceso de cobros dependa del tiempo de respuesta del servicio de licencias.

    \item \textbf{Protocolo:}
    AMQP (Advanced Message Queuing Protocol).

    \item \textbf{Middleware:}
    RabbitMQ (Exchange de tipo Topic).

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Tiempo máximo:}
        Responde al requisito R4 de revocar accesos en menos de 5 minutos. Si la notificación A3 se entrega correctamente a AUT, la memoria caché se invalida de inmediato y el acceso se bloquea en un máximo de 3 minutos
        (lo que tarda en expirar el token activo). En caso de no entregarse el aviso A3, la invalidación ocurre en 4 minutos debido a la expiración del TTL de la memoria caché (60 s) sumado al tiempo del token (3 min),
        coincidiendo con la ventana temporal del diseño síncrono S3.


        \item \textit{Alternativa descartada:}
        Se descartó hacer peticiones síncronas periódicas desde AUT hacia PAG, ya que generaría tráfico de red innecesario y acoplamiento directo entre ambos servicios. 

        \item \textit{Si el receptor no responde:}
        Se utiliza entrega con confirmación explicita (\textit{manual ACK}). Si AUT cae, RabbitMQ mantiene los mensajes persistidos en la cola. Tras superar el límite de 
        reintentos, los eventos fallidos se envían a una (\textit{Dead Letter Queue}) (DLQ) para auditarlos sin descartar notificaciones.
    \end{itemize}
\end{itemize}
