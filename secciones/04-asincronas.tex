\section{Interacciones asíncronas y tolerancia a fallos}
\label{sec:asincronas}

En la plataforma de OndaPlay empleamos comunicación asíncrona para aquellos flujos donde el emisor no requiere una respuesta rápida para continuar con su flujo de 
trabajo, prorizando la disponibilidad y la baja latencia al usuario final. Seleccionamos apache kafka como el middleware principal de mensajería para manejar la
 ingesta masiva y el procesamiento de eventos de telemetría y recomendacionesn, mientras que RabbitMQ se usa para la propagación de eventos de dominio críticos entre 
 facturacíon y licencias.

\subsection{A1: Envío de telemetría (Reproductor $\rightarrow$ Telemetría)}
\label{sub:a1}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:} 
    `CLI` (Reproductor en app/web/TV) $\rightarrow$ Servicio de Telemetría (via API Gateway).

    \item \textbf{Mensaje:}
    Evento en JSON con los campos: \texttt{user\_id}, \texttt{content\_id}, \texttt{event\_type}, (play, pause, buffer\_empty, quality\_change), \texttt{timestamp} y \texttt{metrics} (bitrate actual, fotogramas perdidos).

    \item \textbf{Tipo:}
    Punto a punto (Cliente a API de Ingesta).

    \item \textbf{Por qué es asíncrona:}
    El reproductor no debe de bloquear la interfaz ni la reproduccion del video esperando a que el servidor procese las métricas enviadas.

    \item \textbf{Protocolo:}
    HTTP/2 mediante peticiones REST/JSON sobre HTTPS.

    \item \textbf{Middleware:}
    Nginx como API Gateway enviando el flujo hacia apache Kafka.

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Volumen:}
        Cumple con el requisito R3 al soportar 5\,000 eventos/s generados durante transmisiones en vivo con 50\,000 espectadores emitiendo un reporte cada 10 segundos.

        \item \textit{Pérdida tolerada:}
        Según R3, se acepta perder hasta un 1\,\% de los mensajes de telemetría sin que afecte a la métrica global ni interrumpa el servicio al usuario.

        \item \textit{Alternativa descartada:}
        Se descartó gRPC/RPC síncrono porque acoplaría el cliente al tiempo de respuesta del servidor y añadiría sobrecarga innecesaria por confirmación en cada evento de 10 segundos.

        \item \textit{Si el receptor no responde:}
        El cliente guarda un buffer circular en memoria local de los últimos 3 a 5 eventos. Si la falla persiste y el buffer se llena, descarta los paquetes viejos respetando el 1\,\% de pérdida tolerado.
    \end{itemize}
\end{itemize}

\subsection{A2: Eventos de visualización (Telemetría $\rightarrow$ Recomendaciones)}
\label{sub:a2}

\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    Servicio de Telemetría $\rightarrow$ `MSG` (Apache Kafka) $\rightarrow$ servicio de Recomendaciones.

    \item \textbf{Mensaje:}
    Objeto consolidado del evento visto \texttt{user\_id}, \texttt{content\_id}, \texttt{watch\_duration\_seconds}, \texttt{completion\_percentage}, \texttt{timestamps}.

    \item \textbf{Tipo:}
    Publicacion / Suscripción (Pub/Sub).

    \item \textbf{Por qué es asíncrona:}
    El procesamiento de algoritmos de recomendación consume bastantes recursos y no es necesario actualizar el perfil del usuario en tiempo real instante a instante.

    \item \textbf{Protocolo:}
    Protocolo binario de Kafka sobre TCP.

    \item \textbf{Middleware:}
    Apache Kafka (Topic de telemetría procesada).

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Retraso aceptable:}
        Se ajusta al requisito R5, el cual permite hasta 15 minutos de restraso en la actualización del catálogo de recomendaciones (consistencia eventual).

        \item \textit{Alternativa descartada:}
        Se descartó RabbitMQ en memoria porque Kafka ofrece una persistencia en disco basada en archivos de registro (\textit{commit logs}) mucho más eficiente para volúmenes altos en tiempo real.

        \item \textit{Si el receptor no responde:}
        Frente al escenario F2 (Recomendaciones caído por 2 horas), los mensajes se quedan retenidos de forma segura en las particiones del Topic de Kafka. Al volver
         a estar en línea, el seervicio lee desde el último \textit{offset} guardado y procesa el atraso sin perder ningún evento de visualización.
    \end{itemize}
\end{itemize}

\subsection{A3: Cambio de suscripción (Facturación $\rightarrow$ Licencias)}
\label{sub:a3}


\begin{itemize}
    \item \textbf{Emisor $\rightarrow$ receptor:}
    `PAG` (Servivio de Facturación) $\rightarrow$ `MSG` (RabbitMQ) $\rightarrow$ `AUT` (Servicio de Licencias).

    \item \textbf{Mensaje:}
    Evento de dominio en JSON: \texttt{event\_id}, \texttt{user\_id}, \texttt{event\_type}, (SUBSCRIPTION\_CANCELLED, RENEWED, PAYMENT\_FAILED), \texttt{expiration\_timestamp}.

    \item \textbf{Tipo:}
    Publicación / Suscripción (Pub/Sub).

    \item \textbf{Por qué es asíncrona:}
    Evita que la pasarela de pagos o el proceso de cobros dependa del tiempo de respuesta del servicio de licencias o de la base de datos de usuarios.

    \item \textbf{Protocolo:}
    AMQP (Advanced Message Queuing Protocol).

    \item \textbf{Middleware:}
    RabbitMQ (Exchangue de tipo Topic).

    \item \textbf{Justificación:}
    \begin{itemize}
        \item \textit{Tiempo máximo:}
        Responde al requisito R4, garantizando que el bloqueo ocurra en menos de 5 minutos. Al recibir el evento A3, el servicio `AUT` invalida de inmediato la memoria caché (Redis),
        lo que encaja con los 4 minutos máximos contemplados en el flujo sincrono S3 (60 s de TTL en caché + 3 min de expiración de token.)

        \item \textit{Alternativa descartada:}
        Se descartó hacer \textit{polling} periódicos desde Licencias a la base de datos de Facturación, ya que generaría miles de consultas innecesarias a la base de datos central.

        \item \textit{Si el receptor no responde:}
        Se utiliza entrega con confirmación explicita (\textit{manual ACK}. Si `AUT` cae, RabbitMQ mantiene los mensajes persistidos en la cola. Tras superar el límite de 
        reintentos, los eventos fallidos se envían a una \textit{Dead Letter Queue} (DLQ) para auditarlos sin descartar notificaciones ).
    \end{itemize}
\end{itemize}
